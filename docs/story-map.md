# ストーリーマップ（Phase 1）

今のキュー打ちの作業を観察し、アプリを入れたあとの作業の流れを並べて、MVP の範囲を線で切る。

## 1. 今の作業の観察（2026-10-26 のヒアリング）

### 状況

| 項目 | 内容 |
|---|---|
| 1 回に処理する曲数 | ケースバイケース（100 曲以上〜1、2 曲）。**このアプリは 10 曲以上をまとめて処理する場面を想定する**。1、2 曲なら手作業でよい |
| 環境 | Mac とヘッドホンだけ（XDJ-RR はつながない） |
| かかる時間 | 2 分ほどの曲 5 曲で 10 分以上（1 曲あたり 2 分以上。2026-10-30 の計測。ヒアリングでは曲の合計 30 分ぶんで約 15 分の見積もりだった） |
| 前後の作業 | myTag 付け、プレイリスト作り、USB への書き出しを同じタイミングでやることが多い |

### 今の手順（1 曲ごとに繰り返す）

1. Rekordbox の解析を待つ
2. エクスポートモードで曲を 1 曲ロードする
3. 頭から再生して、イントロのメモリーキューを打つ
4. サビ・メインを聴いて、ホットキューを打つ ← **時間がかかる**
5. 抜けを探して、メモリーキューを打つ ← **時間がかかる**
6. アウトロを聴いて、アウトロがあれば H とメモリーキューを打つ
7. 次の曲をロードする

### 分かったこと

- **波形などで当たりは付けているが、結局毎回頭から飛ばし聴きしている。** 当たりを信用できないので通して聴いている。concept.md の「曲を通して聴かずに済むこと」が価値の中心だという見立てと合っている
- **時間がかかるのはメインと抜けを探すところ。** 抜けは MVP に入れないことにした（2026-10-26 確認。Phase 0 の「やらないことリスト」どおり）。抜けは今までどおり自分で探す
- **グリッドを手で直す曲は 1〜2 割で、Pops や Jazz に多い。** MVP の対象（House / UKG / 2-step / Afro）ではグリッドはおおむね正しいと見てよさそう【仮説】
- **手が止まるのは次の 2 つ。**
  - どこがサビ・メインなのか分からない曲
  - 途中で構成が微妙にずらされる曲（パートの頭が 2 拍ずれるなど）。曲の頭から 8 / 16 小節ずつ数えるだけのルールでは外れる。こういう曲は「要確認」にしたい

## 2. 目標の確認

- 目標は **ユーザーが手を動かす時間を今の 1/3 以下** にすること（concept.md 4 章）
- アプリの推定にかかる時間は含めない。推定中、ユーザーは別のことをしていればよい
- そのため、推定は **まとめて実行して放っておける**（途中で操作を求めない）ことが大事になる。1 曲あたりの処理速度は優先しない（トレードオフスライダー 5 位のまま）

## 3. ストーリーマップ

アプリを入れたあとの流れを左から右に並べる。縦は各ステップでやること。
**MVP** の行が MVP に入れるもの、**後** は MVP のあと、**既存** は Rekordbox の機能をそのまま使うもの。

| | ① 曲を用意する | ② 自動でキューを打つ | ③ Rekordbox に反映する | ④ 確認・修正する | ⑤ 仕上げる |
|---|---|---|---|---|---|
| **既存** | 曲を入れて解析する／必要ならグリッドを直す | | | キューの位置に飛んで聴く／ずれていれば打ち直す | myTag 付け、USB への書き出し |
| **MVP** | キューを打つ曲をプレイリストにまとめる | ライブラリ（master.db のコピー）を読み、指定したプレイリストの曲をまとめて処理する（ADR 0003） | Rekordbox を閉じてアプリが master.db に書く手順が決まっている（スパイク 4、ADR 0001） | 要確認の曲と理由の一覧を見て、どこを重点的に聴くか分かる | |
| **MVP** | | 必ず打つ 4 つのキュー（A メロの頭、その 2L 前、2 回目以降のメインのホットキュー、アウトロの H）を打つ | 既に手動キューがある曲は上書きしない | | |
| **MVP** | | 自信のない曲・キューに「要確認」を付ける（構成のずれ、メインが分からない、など） | | | |
| **後** | | 抜けのメモリーキュー、イントロの細かい区切り、アウトロの L 小節ごとのキュー | | 修正した結果を取り込んで、推定の精度を測る・学習に使う | |
| **後** | | MCP から実行する | | | |

### MVP で確かめたい仮説

> 必ず打つ 4 つのキューと「要確認」の一覧があれば、ユーザーは曲を通して聴かずに、要確認のところだけ聴いて直せばよくなり、キュー打ちに使う時間が今の 1/3 以下になる

## 4. 論点（要相談）

決定済み：抜けのメモリーキューは MVP に入れない（2026-10-26）。抜け探しの時間が残るため、1/3 に届くかは MVP を使って確かめる。


1. ~~今の作業時間をもう少し正確に測るか~~ → 2026-10-30 に測った（2 分ほどの曲 5 曲で 10 分以上）。これを 1/3 の基準にする（requirements.md 1 章）
2. ~~要確認の一覧をどこで見せるか~~ → ターミナルに表示し、同じ内容を CSV にも保存する（requirements.md の決定 13、2026-10-30）

## 5. 技術スパイク

一番不確かな部分を、短い調査で先に確かめる。結果は `docs/spikes/` にまとめる。

| # | 確かめること | 関係するストーリー |
|---|---|---|
| 1 | 音源分離によるボーカルの入りの検出が M4 / 16GB で現実的か（速度、メモリ、精度） | A メロの頭を打つ |
| 2 | Rekordbox のフレーズ解析の結果を読み出せるか（XML、pyrekordbox など） | メイン・抜けの候補を得る |
| 3 | XML を取り込んだとき、既存のキューがどう扱われるか（上書き、追加、重複） | Rekordbox に反映する |
| 4 | master.db にキューを直接書けるか（スパイク 3 の結果を受けて追加） | Rekordbox に反映する |
