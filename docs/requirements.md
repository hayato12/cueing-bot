## 前提（Phase 1 までに分かったこと）

- MVP で打つのは **必ず打つ 4 つのキュー**：A メロの頭（メモリー）、その 2L 小節前（メモリー）、2 回目以降のメインの終わりの 2L 前（ホット A〜G）、アウトロの頭（ホット H）。あわせて、自信のない曲・キューに「要確認」を付ける（[story-map.md](story-map.md)）
- **Rekordbox 7.2.18 の XML 取り込みでは、メモリーキューは 1 曲に 1 つしか入らない。** 取り込むと曲のキューは XML の内容に丸ごと置き換わる（[spikes/03-xml-import.md](spikes/03-xml-import.md)）。反映の方式は、スパイク 4 の結果から master.db への直接書き込みに決めた（[ADR 0001](adr/0001-write-cues-to-master-db.md)）
- 評価のデータには、オーナーが打った約 1,500 曲の手動キューが使える。手動キューから「A メロの頭」を推定するルールは、オーナーの答えと 10 曲中 7 曲で合った（[spikes/01-vocal-detection.md](spikes/01-vocal-detection.md)）

## 1. 評価指標と目標値

### 決定

- **正解は「オーナーが実際に打つ位置」。** 音楽上の区切りと違っても、オーナーが実用上そこに打つなら、そこを正解にする（2026-10-28）
- **評価は反映の方式と切り離す。** アプリが推定したキューの位置（小節）と正解を比べる。どう Rekordbox に入れるかは評価に関係させない
- 最終的な成功の基準は concept.md 4 章のとおり、**ユーザーが手を動かす時間が今の 1/3 以下**。下の指標は、そこに近づいているかを開発中に数字で見るためのもの

### 指標（決定、2026-10-30）

| # | 指標 | 内容 | 見る理由 |
|---|---|---|---|
| M1 | キューごとの的中率 | 4 つのキューそれぞれについて、推定と正解が **同じ小節** の割合 | 1 小節でもずれれば打ち直しになるので、手間に直結する |
| M2 | 曲ごとの全的中率 | 4 つのキューが全部当たった曲の割合 | 「確認だけで直さずに済む曲」の割合 |
| M3 | 要確認の精度 | 「要確認」を付けなかった曲のうち、4 つとも当たった曲の割合 | 要確認でない曲を流し見で済ませてよいかの目安 |
| M4 | 要確認の割合 | 「要確認」を付けた曲の割合 | 高すぎると、結局全部聴くことになる。M3 とトレードオフ |
| M5 | 作業時間 | 10 曲以上をまとめて処理したときの、ユーザーの作業時間（確認・修正・反映） | 最終的な成功の基準。Sprint 3 の実戦投入で測る |

M1〜M4 は評価スクリプトで毎回出す。M5 は実際に使って測る。

- **当たりの基準**：**同じ小節** を当たりにする（M1〜M3 の目標に使う）。±1 小節以内の数字も参考として一緒に出す
- **評価データ**：開発中は手動キューから自動で作ったデータ（約 1,500 曲、MVP の対象ジャンルでは数百曲。正解の取り出しが 3 割ほど外れる）で傾向を見る。目標を満たしたかの判定は、**オーナーが確認した 30 曲ほど** で行う
- **目標値**：下の仮の値にしておき、Sprint 2 でルールベースの数字が出たら決め直す

| 指標 | 仮の値 | 考え方 |
|---|---|---|
| M1（同じ小節） | 4 つのキューそれぞれ 70% 以上 | 10 個中 3 個の打ち直しなら、全部聴くより明らかに速い、という見立て |
| M3 | 80% 以上 | 要確認でない曲の 5 曲に 1 曲は直すことになるが、流し見で見つけられる範囲 |
| M4 | 40% 以下 | 要確認が半分を超えると、全部聴くのと変わらなくなる |
| M5 | 今の 1/3 以下 | concept.md の目標どおり。基準は下のとおり |

### 今の作業時間（M5 の基準）

- **2026-10-30 の計測：2 分ほどの曲 5 曲（曲の合計 10 分ぶん）で 10 分以上**（1 曲あたり 2 分以上）。**これを基準にする**（2026-10-30 オーナー決定）。concept.md 4 章も合わせて直した
  - ヒアリングのときの見積もり（曲の合計 30 分ぶんで約 15 分）とは、曲の長さあたりでは 2 倍以上違うが、1 曲あたりでは同じくらい
- 1/3 にするには、**1 曲あたり 40 秒ほど以下**（5 曲で 3 分 20 秒ほど以下）にする必要がある
- 「4 つのキュー」と「それ以外（抜けなど）」の内訳はまだ測っていない。抜けのメモリーキューは MVP の対象外なので、抜け探しの時間はアプリを入れても残る。次に測るときは内訳も取る

### 受け入れ基準（2026-10-30 オーナー確認）

**S1 評価**
- 手動キューから、4 つのキューの正解を取り出せる（評価データ a）。取り出せなかった曲は理由付きで除く
- オーナーが確認した評価データ b（30 曲ほど）を読み込める
- M1〜M4 を出す。M1・M3 は「同じ小節」と「±1 小節以内」の両方を出す
- 結果を日付付きで保存し、前回と比べられる
- 推定部分を差し替えても（ルール → ML）、評価はそのまま使える

**S2 まとめて推定**
- プレイリストの名前を指定すると、その曲だけを推定する
- 実行中に操作を求めない（N4）。失敗した曲は飛ばし、最後に一覧で知らせる。やり直しでは終わった曲を飛ばす（N9）
- 平均 60 秒／曲以内、ピーク 8GB 以下（N7・N8）
- ライブラリには書き込まない（推定だけ）

**S3 4 つのキュー**
- 4 つのキュー（A メロの頭、その 2L 小節前、2 回目以降のメインの終わりの 2L 前のホット A〜G、アウトロの頭のホット H）を、小節の 1 拍目の位置で出す
- 評価データ b で、M1 が各キュー 70% 以上（仮の値。Sprint 2 のあとで決め直す）
- 推定部分は差し替えられる形にする（入力：曲の情報、出力：推定キューのリスト）

**S4 要確認**
- 曲ごと・キューごとに「要確認」と理由を付ける。理由の最初の候補：
  - 曲の構成がテンプレートからずれている（パートの頭が拍単位でずれる、など）
  - メインがどこか分からない
  - イントロにボーカルの断片がある（スパイク 1）
  - 書き込みを確かめていない音源の形式（N10）
  - ビートグリッドのテンポが一定でない
- 評価データ b で、M3 が 80% 以上、M4 が 40% 以下（仮の値）

**S5 要確認の一覧**
- 要確認の曲を、理由と「どのキューを聴けばよいか」（小節番号）付きで一覧にする。ターミナルに表示し、同じ内容を CSV にも保存する（決定 13）
- 要確認でない曲も、4 つのキューの小節番号を一覧で見られる

**S6 Rekordbox に反映**
- ADR 0001 の 5 つの決めごとと N1〜N3・N10・N12 を守る（Rekordbox 終了中だけ、毎回バックアップ、書く内容を先に見せる、など）
- 反映したあと、Rekordbox の画面で 4 つのキューが見え、それぞれの位置から再生できる
- 手動キューが 1 つでもある曲には書かず、一覧で「手動キューあり」と知らせる（決定 11）
- 反映した曲のプレイリスト・myTag・レーティングは変わらない。ほかの曲は何も変わらない
- 反映をやめたいときは、バックアップから戻せる（手順は README）

### 決定（2026-10-30 オーナー確認）

| # | 決めたこと | 選ばなかった案 |
|---|---|---|
| 11 | **既に手動キューがある曲は丸ごと飛ばす。** キューが 1 つでもある曲には書かず、一覧で「手動キューあり」と知らせる。手で打ったキューを絶対に壊さない | 足りないキューだけ足す、アプリのキューで置き換える |
| 12 | **ホットキューも DB に書く。** 4 つのキューを全部書く | メモリーキューだけ書く |
| 13 | **要確認の一覧はターミナルに表示し、同じ内容を CSV にも保存する。** CSV は曲名入りなので、リポジトリの外に置く | ターミナルだけ、Rekordbox のコメント欄や myTag に書く |

## 4. 反映の方式

- **master.db に直接書く**（[ADR 0001](adr/0001-write-cues-to-master-db.md)、2026-10-30 オーナー承認）。XML の取り込みはキューの反映には使わない
- 書くときは ADR 0001 の 5 つの決めごと（Rekordbox を終了してから書く、毎回バックアップ、Rekordbox と同じ形、対象の曲だけ、書く内容を先に見せる）を守る。確かめたバージョンと違えば警告する

### 決定（3 章から）

- 既存の手動キューがある曲は丸ごと飛ばす（3 章の決定 11）
- ホットキューも DB に書く（3 章の決定 12）

## 5. 完成の定義（Definition of Done）

ストーリー（Issue）を「完成」と言うための共通の条件。受け入れ基準（ストーリーごと）に加えて、すべてのストーリーで満たす。

### どのストーリーにも共通の条件（2026-10-30 オーナー確認）

| # | 条件 | 理由 |
|---|---|---|
| D1 | 受け入れ基準をすべて満たした | ストーリーごとの完成の条件 |
| D2 | 自動テストが通る（個人のデータを使わないテスト） | DX・テスト自動化を大事にする（CLAUDE.md 3 章） |
| D3 | 推定のロジックを変えたときは、評価スクリプトの M1〜M4 を記録した（集計の数字だけをリポジトリに残す） | 「数値で改善を確認する」（CLAUDE.md 5 章） |
| D4 | 大きな方針を決めたときは ADR を書いた | CLAUDE.md 5 章 |
| D5 | 使い方・再現の手順が README か docs に書いてある | GitHub で公開できる状態に保つ |
| D6 | 音源・ライブラリのデータ（XML、DB のコピー、解析ファイル、曲名入りの CSV）がリポジトリに入っていない | N6 |
| D7 | DB に書くコードを変えたときは、テスト用の曲（デモ曲のコピー）で書いて、Rekordbox の画面で確かめた。戻す手順（N3）も、最初に一度テスト用の曲で試した | ADR 0001。本物の曲で初めて試さない |
| D8 | 多段レビュー（下の決定）を通し、指摘をすべて直すか理由を付けて閉じ、オーナーが見て main に入れた | development-process.md Phase 4（実装は小さなブランチと PR、Claude Code にレビューさせる） |

### 決定（2026-10-30 オーナー確認）

- **14. 個人データを使わないテストは GitHub Actions でも回す。** DB への書き込みや実際の曲を使う確認（D7）は Mac で手で行う。オーナーの条件は「Actions の無料枠に収まること」。リポジトリは公開（public）なので、GitHub が用意する標準の実行環境（Linux など）なら Actions は無料で、時間の上限もない。macOS の実行環境も公開リポジトリなら無料だが、要らなければ Linux で回す
- **16. スプリント単位の条件は、Sprint 3（MVP 完成）だけ「実際に 10 曲以上で使い、M5 の作業時間を測った」とする。** Sprint 1・2 は評価の数字で判断する

### 決定：レビューのやり方（多段レビュー、2026-10-30 オーナー確認）

Anthropic の Claude Code チームの多段レビュー（[Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/)）を、個人開発に合う範囲で取り入れる。

- **PR の単位**：ストーリーごと（1 Issue 1 ブランチ 1 PR）。development-process.md Phase 4 の「小さなブランチと PR」
- **PR の前**：作者側の Claude がテストとリンターを回して出力を見せ、`/code-review` と `/security-review` をローカルで通す。結果は PR の説明に載せる。指摘は直すか、理由を付けて閉じる
- **REVIEW.md**：何を重く見るかを書く（ライブラリを壊す、個人データが入る、評価の数字をごまかす、など）。レビューのたびに CLAUDE.md と一緒に読ませる
- **CI を必須にする**：テストとリンターが GitHub Actions で通らないとマージしない（決定 14）
- **PR テンプレート**：「どう確かめたか」「どう戻すか」の欄を必ず書く
- **往復は 3 回まで**：レビューと修正の往復が 3 回を超えたら、やり方そのものを見直す。2 回目以降のレビューは、前回からの差分だけを見る
- **最後はオーナーが見てマージする。** Claude の承認は、人の承認に数えない
- 記事の段階 6〜7（マージキュー、段階的なリリースなど）は、個人開発には大きすぎるのでやらない。戻すのは git の revert と DB のバックアップで足りる

- **PR ごとの自動 AI レビュー（GitHub Action）は入れない**（2026-10-30 オーナー決定）。Anthropic の API キーと従量課金が要るため。レビューは PR の前に `/code-review` と `/security-review` をローカルで回し、**その結果を PR の説明に載せる**

REVIEW.md と PR テンプレート、CI の設定は Sprint 0（リポジトリ整備）で作る。

### 注意

- テストやリンター（コードの書き方のチェック）の道具は [ADR 0002](adr/0002-python-and-tooling.md) で決めた（pytest・ruff・pyright）。D2 は「これらがすべて通る」の意味
