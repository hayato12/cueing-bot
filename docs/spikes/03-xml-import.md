# スパイク 3：XML を取り込んだとき既存のキューがどう扱われるか

状態：**完了**（2026-10-26〜28。1 回目、追加の実験、切り分けの実験、原因の切り分け）

## 問い

アプリが出力した XML を Rekordbox に取り込むと、曲にもともとあるキューは消えるのか、残るのか、重複するのか。

## 環境

| 項目 | 内容 |
|---|---|
| マシン | MacBook Pro M4 / 16GB |
| Rekordbox | 7.2.18 |
| Python | 3.10（pyenv）。スクリプトは標準ライブラリだけなので venv も不要。環境管理ツールは未決定のまま |

## 手順

1. 曲 A〜D をコレクションに追加して解析し、上の表どおりにキューを打つ
2. コレクションを XML でエクスポートする（`export.xml`、リポジトリの外に置く）
3. [scripts/spikes/spike3_make_import_xml.py](../../scripts/spikes/spike3_make_import_xml.py) で取り込み用の `import.xml` を作る
4. 1 回目：`rekordbox xml` の画面で曲 A〜D を 1 曲ずつ選び「コレクションにインポート」。終わったらエクスポート（`after1.xml`）
5. 2 回目：同じ XML のプレイリスト `spike3` を「プレイリストをインポート」。終わったらエクスポート（`after2.xml`）。同じ XML を 2 回取り込んだときに重複するか、取り込み方で違うかを見る
6. `export.xml`・`after1.xml`・`after2.xml` のキューを比べる

### 曲の情報

- A〜C（属性をすべて写した曲）：TrackID 以外は変わらなかった
- D（TrackID・Name・Location だけの曲）：アーティスト・レーベル・コメントが空になり、Size が 0、追加日が取り込んだ日に変わった。BPM・キー・ビートグリッド（TEMPO）は残った
- **取り込んだ 4 曲はすべて TrackID が変わった。** ほかの 3,093 曲は、TrackID も含めて何も変わらなかった
- **取り込んだ 4 曲は、既存のプレイリストから外れた。** 取り込み前は 4 曲ともプレイリスト `cueing bot` に入っていたが、取り込み後は空になった。画面でも空になっていた（TrackID が変わったことと関係がありそう）
- 取り込みのとき、確認のダイアログは出なかった
- 2 回目（プレイリスト単位の取り込み）では、プレイリスト `spike3` ができた以外の変化はなかった。同じ XML をもう一度取り込んでも、キューは重複しなかった

### 分かったこと

1. **取り込みは、曲のキューを XML の内容に丸ごと置き換える（追加ではない）。** XML に書かなかったキューは、メモリーもホットも消える（B の 48.024s、C の H、D の A）
2. ホットキューは、番号ごとに XML の位置・名前で上書きされる。色を書かなくても、A・B は元の色（スロットの既定色？）になった
3. 同じ XML を 2 回取り込んでも重複しない。曲単位でもプレイリスト単位でも結果は同じだった
4. XML に書かなかった曲の情報（アーティストなど）は空で上書きされる。属性はエクスポートの値をすべて写す必要がある
5. **取り込んだ曲は TrackID が変わり、既存のプレイリストから外れる。** 曲をいったん消して入れ直すような動きに見える

## 切り分けの実験（2026-10-28）

メモリーキューが 1 つしか入らないのが、Rekordbox の仕様か、こちらの XML の書き方のせいかを見分けた。
データは `~/llm/cueing-bot/data/spike3/round3/`。

1. 曲 E のメモリーキューを消し、手で 9・25・41 小節目（15.023s、45.023s、75.023s）に打ってエクスポートした（`export.xml`）
2. エクスポートの文字列から E の `<TRACK>` 〜 `</TRACK>` を 1 文字も変えずに切り出し、取り込み用の XML にした（[scripts/spikes/spike3c_extract_track.py](../../scripts/spikes/spike3c_extract_track.py)）
3. Rekordbox で E のメモリーキューを全部消してから、その XML を「コレクションにインポート」した（ダイアログで「はい」）

**結果：入ったのは最後のメモリーキュー 75.023s の 1 つだけだった**（`after.xml` と画面の両方で確認）。

Rekordbox が自分で出力した XML でも同じことが起きたので、**原因はこちらの XML の書き方ではない。Rekordbox 7.2.18 の取り込みが、メモリーキューを 1 つしか残さない**（仕様か不具合かは分からない）。
取り込みの経路にもよらない。1 回目の B（ダイアログが出ず、曲が入れ直された）も、追加の実験と切り分けの実験（ダイアログで「はい」）も、残ったのは最後のメモリーキュー 1 つだった。
Web でも探したが、Rekordbox 自身の XML 取り込みでこの現象を説明している情報は見つからなかった。

## 原因の切り分け（4 回目、2026-10-28）

メモリーキューが 1 つしか入らない理由を、XML の書き方で避けられるかどうかで切り分けた。
データは `~/llm/cueing-bot/data/spike3/round4/`。XML は [scripts/spikes/spike3d_make_variants_xml.py](../../scripts/spikes/spike3d_make_variants_xml.py) で、切り分けの実験の後のエクスポート（`round3/after.xml`）の文字列を元に、POSITION_MARK の行だけを差し替えて作った。

### 仮説

Rekordbox の取り込みは、キューを POSITION_MARK の `Num` ごとに 1 つの枠として扱っている。メモリーキューはどれも `Num="-1"` なので、同じ枠を取り合って最後に書いたものだけが残る。

### 結果

E・F・G は曲ごとに「コレクションにインポート」（ダイアログで「はい」）。N1・N2 はコレクションになかった曲（E の音源のコピー）で、手順の都合で 2 曲とも「プレイリストをインポート」で取り込んだ。

| 曲 | XML に書いたキュー（書いた順） | 取り込み後 |
|---|---|---|
| E | メモリー 15.023s（Num=-1）、45.023s（Num=-2）、75.023s（Num=-3） | **15.023s（Num=-1）だけ**。-2・-3 は入らなかった |
| F | メモリー 16.024s、48.024s、80.024s（Num を書かない） | **キューなし**（既存の 48.024s も消えた） |
| G | ホット A 15.023s、メモリー 30.023s、メモリーループ 45.023〜52.523s（Type=4、Num=-1）、メモリー 75.023s | **ホット A と、メモリー 75.023s（最後に書いたもの）だけ**。ループも消えた |
| N1・N2 | メモリー 15.023s、45.023s、75.023s（すべて Num=-1） | **75.023s（最後に書いたもの）だけ** |

### 分かったこと

10. **`Num="-1"` 以外のメモリーキューは入らない。** -2・-3 や Num なしは無視される。Num を変えて枠を分ける回避策は使えない
11. **メモリーループもメモリーキューと同じ 1 枠を取り合う。** G では、後に書いたメモリーキューがループを上書きした
12. **新しい曲として入れても同じ。** 既存の曲を更新する処理だけの問題ではない（ただし、新しい曲を「コレクションにインポート」で入れる経路は試していない）
13. 仮説（`Num` ごとに 1 枠、最後に書いたものが勝つ）で、1〜4 回目の結果がすべて説明できる。**Rekordbox 7.2.18 の XML 取り込みでは、1 曲に入るメモリーキュー（ループを含む）は 1 つまで。XML の書き方では避けられない**

Web で調べた範囲では、昔のツール（Rekordbox 5.6 向けの [rekordbox-scripts](https://github.com/hiddevanesch/rekordbox-scripts) の「ホットキューをメモリーキューに写す」や、ReCK の Windows 向け XML 変換）は XML でメモリーキューを複数入れる前提で作られていた。以前は入っていて、6〜7 のどこかで変わった可能性が高い。7.2.19（2026-09）のリリースノートは「不具合修正」としか書いておらず、直ったかは分からない。

## 結論と設計への影響

- **取り込むと、曲のキューは XML の内容に丸ごと置き換わる。** 「既に手動キューがある曲は上書きしない」（ストーリーマップの MVP）は、XML の書き方では守れない。アプリの側で、手動キューがある曲を出力から外すか、既存のキューを XML に書き戻す必要がある
- 出力する曲の属性と TEMPO は、エクスポートの値をそのまま写す
- **XML で取り込めるメモリーキューは 1 曲につき 1 つだけ（Rekordbox 7.2.18）。ホットキューは複数入る。** Num を変える・Num を書かない・ループにする・新しい曲として入れる、のどれでも避けられなかった（4 回目）。 「メモリーキューを複数打つ」MVP は、XML の取り込みではそのままでは実現できない。反映方法を見直す必要がある（要件化で相談。下の「選択肢」）
- 取り込みでは確認のダイアログで「はい」を選ぶ。そうすれば TrackID・プレイリスト・レーティング・myTag は残る。ダイアログが出ないときはプレイリストから外れることがあるので、手順に注意を書く
- 解析ロックした曲は、取り込みでビートグリッドとキーが変わらない（ダイアログの文言による。未検証）

### メモリーキューの反映方法の選択肢（未決定）

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| 1. ホットキューで出す | メモリーキューにしたい位置も、空いているホットキュー（A〜H）で出す | XML の取り込みだけで済む。複数入ることは確認済み | 8 個まで。今の使い分け（ホット＝メイン、メモリー＝区切り）が崩れる |
| 2. 1 つはメモリー、残りはホット | 一番大事な 1 つ（例：A メロの頭）だけメモリーキューで出す | 案 1 より今の使い方に近い | どれをメモリーにするかの決めごとが要る |
| 3. 一覧を見て手で打つ | アプリは位置の一覧（小節番号など）を出すだけにする | ライブラリを一切触らない | 手で打つ時間が残り、目標の 1/3 に届きにくい |
| 4. DB に直接書く | pyrekordbox などで master.db に書き込む（CueGen はこの方式） | メモリーキューを好きなだけ書ける | **「DB に書き込まない」という約束（CLAUDE.md）に反する。** 壊れたときの影響が大きい |
| 5. ホットキューで入れて、Rekordbox を自動操作してメモリーキューにする | XML でホットキューを入れた後、キーボードショートカットを自動で押して（Mac の AppleScript など）、ホットキューの位置へ飛び、メモリーキューを打つ。[Bide's Rekordbox AutoCuer](https://github.com/Bide-UK/Bides-Rekordbox-AutoCuer) や ReCK（Mac 版）、Reddit で紹介されていた Automator の方法が近い | DB に書かずにメモリーキューを複数打てる。Rekordbox の正規の操作だけを使う | 1 回に 8 か所まで（ホットキューの数）。画面の操作なので壊れやすく、実行中は Mac を触れない。後から XML を取り込むと、また消える。ショートカットでできるかは未検証 |
