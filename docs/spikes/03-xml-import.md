# スパイク 3：XML を取り込んだとき既存のキューがどう扱われるか

状態：**1 回目（2026-10-26〜28）と追加の実験（2026-10-28）が完了**。メモリーキューが 1 つしか入らない原因だけ未確認

## 問い

アプリが出力した XML を Rekordbox に取り込むと、曲にもともとあるキューは消えるのか、残るのか、重複するのか。

## 手順

1. 曲 A〜D をコレクションに追加して解析し、上の表どおりにキューを打つ
2. コレクションを XML でエクスポートする（`export.xml`、リポジトリの外に置く）
3. [scripts/spikes/spike3_make_import_xml.py](../../scripts/spikes/spike3_make_import_xml.py) で取り込み用の `import.xml` を作る
4. 1 回目：`rekordbox xml` の画面で曲 A〜D を 1 曲ずつ選び「コレクションにインポート」。終わったらエクスポート（`after1.xml`）
5. 2 回目：同じ XML のプレイリスト `spike3` を「プレイリストをインポート」。終わったらエクスポート（`after2.xml`）。同じ XML を 2 回取り込んだときに重複するか、取り込み方で違うかを見る
6. `export.xml`・`after1.xml`・`after2.xml` のキューを比べる

エクスポート 3 つ（取り込み前 `export.xml`、1 回目の後 `after1.xml`、2 回目の後 `after2.xml`）を

### キュー

|---|---|---|---|

| C | ホット A 15.023s、B 45.023s、H 75.023s | ホット A 105.023s、B 45.023s、メモリー 135.023s | **XML どおり**（ホット A 105.023s、B 45.023s、メモリー 135.023s）。H は消えた |
| D | ホット A 16.024s | メモリー 32.024s だけ（曲の情報は最小限） | **キューなし**。ホット A は消え、XML のメモリーキューも入らなかった |

### 曲の情報

- A〜C（属性をすべて写した曲）：TrackID 以外は変わらなかった
- D（TrackID・Name・Location だけの曲）：アーティスト・レーベル・コメントが空になり、Size が 0、追加日が取り込んだ日に変わった。BPM・キー・ビートグリッド（TEMPO）は残った
- **取り込んだ 4 曲はすべて TrackID が変わった。** ほかの 3,093 曲は、TrackID も含めて何も変わらなかった
- **取り込んだ 4 曲は、既存のプレイリストから外れた。** 取り込み前は 4 曲ともプレイリスト `cueing bot` に入っていたが、取り込み後は空になった。画面でも空になっていた（TrackID が変わったことと関係がありそう）
- 取り込みのとき、確認のダイアログは出なかった
- 2 回目（プレイリスト単位の取り込み）では、プレイリスト `spike3` ができた以外の変化はなかった。同じ XML をもう一度取り込んでも、キューは重複しなかった

### 分かったこと

1. **取り込みは、曲のキューを XML の内容に丸ごと置き換える（追加ではない）。** XML に書かなかったキューは、メモリーもホットも消える（B の 48.024s、C の H、D の A）
2. ホットキューは、番号ごとに XML の位置・名前で上書きされる。色を書かなくても、A・B は元の色（スロットの既定色？）になった
3. 同じ XML を 2 回取り込んでも重複しない。曲単位でもプレイリスト単位でも結果は同じだった
4. XML に書かなかった曲の情報（アーティストなど）は空で上書きされる。属性はエクスポートの値をすべて写す必要がある
5. **取り込んだ曲は TrackID が変わり、既存のプレイリストから外れる。** 曲をいったん消して入れ直すような動きに見える

### 結果

| 曲 | 取り込み前 | XML に書いたキュー（書いた順） | 取り込み後 |
|---|---|---|---|
| E | なし | メモリー 15.023s、45.023s、75.023s | **メモリー 75.023s だけ**（最後に書いたもの） |

### 分かったこと

6. **XML にメモリーキューを複数書いても、入るのは最後の 1 つだけ。** 「既存と同じ位置だから入らない」のではない。1 回目の B もこれで説明できる。ホットキューは複数入る（1 回目の C）
7. **ダイアログが出て「はい」を選んだ場合は、TrackID・プレイリスト・レーティング・myTag が残る。** キューだけが XML の内容に置き換わる
8. 1 回目でプレイリストから外れたのは、ダイアログが出ずに曲が入れ直されたからだと考えられる。何がダイアログの有無を分けるのかは分かっていない
9. 解析ロックした曲は、取り込みでビートグリッドとキーが変わらない（ダイアログの文言による。未検証）

### まだ分からないこと

- **メモリーキューが 1 つしか入らないのは、Rekordbox の仕様か、こちらの XML の書き方のせいか。** 書き方は Rekordbox のエクスポートと同じ（`Name`・`Type`・`Start`・`Num="-1"`）。オーナーのライブラリでは 777 曲がメモリーキューを 3 つ以上持っている。Rekordbox が自分で出力した XML をそのまま取り込んでも 1 つになるなら、Rekordbox の仕様と言える
- 1 回目でダイアログが出なかった理由
- D で XML のメモリーキューが入らなかった理由（属性が少なすぎたからと考えられる。アプリでは属性をすべて写すので、追わない）

## 結論と設計への影響

- **取り込むと、曲のキューは XML の内容に丸ごと置き換わる。** 「既に手動キューがある曲は上書きしない」（ストーリーマップの MVP）は、XML の書き方では守れない。アプリの側で、手動キューがある曲を出力から外すか、既存のキューを XML に書き戻す必要がある
- 出力する曲の属性と TEMPO は、エクスポートの値をそのまま写す
- **メモリーキューが 1 つしか入らないなら、XML でメモリーキューを複数打つ MVP は成り立たない。** 原因を確かめたうえで、Hot Cue を使う、別の反映方法を探す、などを検討する必要がある
- 取り込みでは確認のダイアログで「はい」を選ぶ。ダイアログが出ないときはプレイリストから外れることがあるので、手順に注意を書く
