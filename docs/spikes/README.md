# 技術スパイク（Phase 1）

ストーリーマップ（[story-map.md](../story-map.md)）の中で一番不確かな部分を、短い調査で先に確かめる。
1 つのスパイクは半日〜1 日で終える。結果はスパイクごとに `docs/spikes/NN-タイトル.md` にまとめる。

**共通の約束**

- ユーザーの Rekordbox ライブラリを壊さない。DB には書き込まない（例外：スパイク 4 は、オーナーの仮決定で DB への書き込みを試す。書く前にバックアップを取り、テスト用の曲だけに書く）。スパイク 3 の XML 取り込みは、本番のライブラリとは別のテスト用の曲（コピーしたファイル）で試す
- 音源や個人のライブラリデータ（エクスポート XML、解析ファイル）はリポジトリに入れない。手元の Mac の中だけで扱う
- 実行するのはオーナーの Mac（M4 / 16GB）

## 進める順番

| 順番 | スパイク | 理由 |
|---|---|---|
| 1 | 3. XML 取り込みの挙動 | 一番安く確かめられる。結果次第で「反映する」ステップの設計が変わる（上書きされるなら、キューのある曲を除く処理が必須になる） |
| 2 | 2. フレーズ解析の読み出し | 読み出せれば、メインの位置の候補がすぐ手に入る。スパイク 1 の評価にも使える |
| 3 | 1. ボーカルの入りの検出 | 一番重く、不確かさも大きい。スパイク 2 の結果と比べられるよう最後にする |

## スパイク 3：XML を取り込んだとき既存のキューがどう扱われるか

**問い**：アプリが出力した XML を Rekordbox に取り込むと、曲にもともとあるキューは消えるのか、残るのか、重複するのか。

**やり方**

1. テスト用の曲を 3 曲ほど用意する（ライブラリの曲のファイルをコピーし、別名で Rekordbox に入れる）
2. 曲ごとに状態を変えておく：キューなし／メモリーキューだけあり／ホットキュー A と H あり
3. その 3 曲のキューを書いた XML を小さなスクリプトで作る（既存と同じ位置、違う位置、同じホットキュー番号に別の位置、を混ぜる）
4. Rekordbox の「rekordbox xml」から取り込み、各曲のキューがどうなったかを記録する

**分かればよいこと**：メモリーキュー・ホットキューそれぞれについて、上書き／追加／無視のどれになるか。取り込みのやり方（コレクションへのインポート、曲単位のインポートなど）で違いがあるか。

## スパイク 2：Rekordbox のフレーズ解析を読み出せるか

**問い**：Rekordbox のフレーズ解析（Intro / Up / Chorus / Down / Outro などの区切り）を、プログラムから読み出せるか。

**見立て【未確認】**：XML のエクスポートにはフレーズ解析は入っていない。フレーズ解析は曲ごとの解析ファイル（`ANLZ*.EXT`）に保存されていて、pyrekordbox で読めるらしい。

**やり方**

1. pyrekordbox を入れ、数曲の解析ファイルからフレーズの区切りを読み出すスクリプトを書く（読み出しのみ）
2. 区切りの位置を小節番号に直し、手動のキュー（メインのホットキュー、A メロの頭）と並べる
3. 「よく 1 小節ずれる」という印象が、どのくらいの曲・どの区切りで起きているかを見る

**分かればよいこと**：読み出せるか。区切りが手動キューとどのくらい一致するか（そのまま使えるか、補正すれば使えるか、使えないか）。

## スパイク 1：音源分離でボーカルの入りを検出できるか

**問い**：音源分離でボーカルだけを取り出し、ボーカルが入る瞬間（A メロの頭）を見つけることが、M4 / 16GB で現実的にできるか。

**やり方**

1. 音源分離のモデル（候補：Demucs。曲の構造まで推定する all-in-one 系も比較候補）を入れる
2. 手動でキューを打ってある曲 10 曲ほどで、ボーカルを取り出す。1 曲あたりの時間とメモリの使用量を測る
3. ボーカルの音量が一定以上になった最初の位置を、小節の頭に寄せて「A メロの頭」とする
4. 手動の A メロの頭と比べて、何曲が ±1 小節以内に入るかを数える

**分かればよいこと**：1 曲あたりの処理時間（まとめて実行して放っておけるなら、数十秒〜数分でもよい）、メモリが足りるか、何割の曲で当たるか。ボーカルのない曲（メインのメロディが入る曲）でどうなるか。
