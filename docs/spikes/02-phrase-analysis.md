# スパイク 2：Rekordbox のフレーズ解析を読み出せるか

状態：**読み出しは完了**（2026-10-29）。手動キューとの比べ方は粗いので、要件化の前に見直す

## 問い

Rekordbox のフレーズ解析（Intro / Up / Chorus / Outro などの区切り）を、プログラムから読み出せるか。読み出せたら、オーナーの手動キューとどのくらい一致するか。

## 分かったこと：読み出し

1. **pyrekordbox でフレーズ解析を読み出せる。** `ANLZ0000.EXT` の `PSSI` タグに、曲の mood（high / mid / low）と、フレーズごとの「頭の拍（ビートグリッドの通し番号）」と種類が入っている
   - 例：テスト曲 E は mood=mid。41 小節目（161 拍目）から Verse2 と読めた。Rekordbox の画面の表示（41 小節目から VERSE2）と一致した
2. ビートグリッドは `ANLZ0000.DAT` の `PQTZ` タグから読める。各拍の時刻と小節内の拍番号（1〜4）が取れるので、フレーズの頭を秒や小節に直せる
3. **解析ファイルと曲の対応付けにはひと手間要る。** Rekordbox 7 の DAT に入っているパスは `?/ファイル名` だけで、フォルダが分からない。今回はファイル名で対応付け、同じファイル名が複数あるものは使わなかった。確実に対応付けるには DB（master.db の曲の表にある解析ファイルのパス）を読む必要がある。読み取りだけでも DB を開くかどうかは、要件化で決める
4. 手動キューのある 1,544 曲のうち 1,527 曲で解析ファイルが見つかった。フレーズ解析がない曲が 4 曲、pyrekordbox が読めない形式の解析ファイルが 11 曲あった（`PVB2` という未対応のタグの警告も出た）
5. 処理時間は、解析ファイル約 3,200 個を全部読んで 15 秒ほど
6. mood の内訳：high 763 曲、mid 665 曲、low 84 曲。mood によってフレーズの種類の名前が変わる（high は Intro / Up / Down / Chorus / Outro、mid・low は Intro / Verse / Bridge / Chorus / Outro）

## 追記：master.db のコピーで対応付ける（2026-10-29）

オーナーの了承を得て、master.db を（`-wal`・`-shm` と一緒に）`~/llm/cueing-bot/data/db/` にコピーし、**コピーだけを** pyrekordbox で開いた。本物の master.db は開いていない・書いていない。コピーはリポジトリに入れない。

- 曲の表（`djmdContent`）の `FolderPath`（曲のファイルのパス）と `AnalysisDataPath`（解析ファイルのパス）で、曲と解析ファイルを対応付けられた
- **手動キューのある曲 1,545 曲すべてが対応付いた**（ファイル名だけで対応付けたときは 1,527 曲）。ファイル名が重なる曲も使える
- 開くときの暗号の鍵は、pyrekordbox が自動で見つけた（追加の設定は要らなかった）
- コピーは Rekordbox の起動中に取った。書き込みの途中を写した可能性はゼロではないが、読み取り用には問題なかった
- 「コピーを読み取り専用で開く」をアプリの方式にするかは、Phase 3（初期設計）の ADR で決める

## 分かったこと：手動キューとの一致（粗い比較）

フレーズの区切りと手動キューの位置を、ビートグリッドの拍の単位で比べた。「一致」はずれ 0 拍、「1 小節以内」は 4 拍以内。
「HOUSE」は、プレイリストの HOUSE フォルダに入っている曲だけで数えたもの。

| 比べたもの | 範囲 | 件数 | 一致 | 1 小節以内 | ずれ大 | 対応なし |
|---|---|---|---|---|---|---|
| 手動キューがフレーズの区切りに乗っているか | 全体 | 8,069 | 41% | 17% | 42% | |
| | HOUSE | 2,324 | 51% | 13% | 36% | |
| イントロの終わり（A メロの頭）に手動キューがあるか | 全体 | 1,497 | 46% | 21% | 33% | |
| | HOUSE | 422 | 51% | 14% | 35% | |
| ホット H と Outro の頭 | 全体 | 336 | 39% | 10% | 46% | 5% |
| | HOUSE | 191 | 44% | 7% | 46% | 3% |
| ホット A〜G と「2 回目以降の Chorus の終わりの 2L 前」 | 全体 | 3,296 | 14% | 6% | 66% | 15% |
| | HOUSE | 937 | 22% | 5% | 66% | 7% |

ずれの内訳（拍）を見ると：

- **「よく 1 小節ずれる」（±4 拍）は、イントロの終わりで 1 割ほど**（-4 拍が 115 件、+4 拍が 57 件。全 1,497 件中）。あるにはあるが、一番多いずれではない
- **ずれ大の多くは 8・16・32 拍（2・4・8 小節）の倍数。** グリッドのずれではなく、「どのフレーズの区切りをイントロの終わり・アウトロ・メインと見るか」が Rekordbox とオーナーで違う、と読める
- ±1〜2 拍のずれも少しある（イントロの終わりで +1 拍が 52 件など）。オーナーの言う「パートの頭が 2 拍ずれる曲」に当たるのかは未確認

## 比べ方の限界

- イントロの終わりは「その位置に一番近い手動キュー」で見ているので、甘めに出る
- ホット A〜G は「Chorus をメイン」と見なしている。mood が high の曲では、メインが Up や Chorus のどちらに当たるのか、まだ確かめていない
- L（4 小節か 8 小節か）は BPM 120 で機械的に分けた。cueing-theory.md では、BPM 120 前後は聴いて決めることになっている
- 同じファイル名の曲を外したので、全曲ではない

## 結論（暫定）

> 追記（2026-10-31）：下の「曲との対応はファイル名頼み」は、追記の master.db のコピーでの対応付けと [ADR 0003](../adr/0003-read-library-from-db-copy.md) で置き換わった。アプリは master.db のコピーの `AnalysisDataPath` で対応付ける。

- **フレーズ解析は読める。** DB を開かずに、解析ファイルだけで取り出せる（曲との対応はファイル名頼み）
- **そのままキューにすると、当たるのは半分前後。** イントロの終わりとアウトロの H は、HOUSE で 5 割前後が拍まで一致し、1 小節以内まで入れると 6 割前後。ホット A〜G（メインの終わりの 2L 前）は 2 割程度
- ずれの多くはフレーズ単位（2・4・8 小節）で、「Rekordbox がどこを Intro / Chorus / Outro と呼ぶか」と、オーナーのキューの付け方の違いに見える。フレーズの区切りは候補として使い、どの区切りを選ぶかをルールや学習で決める、という使い方が考えられる
- 「要確認」の判断材料にも使えそう（フレーズの区切りとルールの予想が合わない曲を要確認にする、など）。要件化で検討する
