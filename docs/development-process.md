# 開発の進め方

アジャイルで進める。最初の 1〜2 週間でコンセプト〜初期設計を軽く回し、そのあとは 1 週間のスプリントを繰り返す。
Phase 0〜3 は完璧にしない。分からないことは「仮説」として残し、スプリントで確かめる。

```
Phase 0 コンセプト   →  Phase 1 具体化  →  Phase 2 要件化  →  Phase 3 初期設計
(なぜ作るか)          (何を作るか)        (どこまでで完成か) (どう作るか)
        └──────── 最初の 1〜2 週間で軽く回す ────────┘
                                ↓
Phase 4 スプリントを繰り返す(計画 → 実装 → 実際の DJ で試す → 振り返り)
                                ↓
Phase 5 公開・まとめ(README、評価結果、全体の振り返り)
```

## Phase 0：コンセプト（なぜ作るか）

- **やること**：解決したい課題、誰の課題か（オーナー自身）、うまくいったと言える状態を言葉にする
- **手法**：インセプションデッキ（エレベーターピッチ、やらないことリスト、トレードオフスライダーなど）
- **成果物**：`docs/concept.md`
- **論点**：キュー打ちを全部自動化したいのか、下書きを作って自分が直す時間を減らしたいのか。どちらにするかで評価指標も UI も変わる
- **出口**：MVP で確かめたい仮説が言葉になっている

## Phase 1：具体化（何を作るか）

- **やること**
  - 今の作業を観察する（手動でキューを打つとき何を聞いてどこに打っているか、1 曲に何分かかるか）
  - ユーザーストーリーマッピングで作業の流れ（曲を選ぶ → 解析 → キュー確認 → 修正 → Rekordbox に反映）を並べ、MVP の範囲を線で切る
  - 一番不確かな部分は技術スパイク（短い調査）で先に確かめる
- **成果物**：`docs/story-map.md`、スパイクの結果メモ
- **論点**：手動キューの統計（例：キューの大半が 8 / 16 小節の区切りにあるか）を見て、ルールベースでどこまで当たるか仮説を立てる。XML インポート時に既存キューがどうなるかもスパイクで確かめる（→ スパイク 3・4 を経て、反映は master.db への直接書き込みに決めた。ADR 0001）

## Phase 2：要件化（どこまでで完成か）

- **やること**
  - プロダクトバックログを作る（GitHub Issues にユーザーストーリーとして登録）
  - 各ストーリーに受け入れ基準を付ける
  - 非機能要件を決める（ライブラリを壊さない、M4 / 16GB で 1 曲あたり何秒以内、など）
  - 評価指標と目標値を決める（例：±1 小節以内の F1 が 0.7 以上）
  - 完成の定義（Definition of Done）を決める（テストが通る、評価スクリプトの数値を記録した、など）
- **成果物**：GitHub Issues、`docs/requirements.md`。Projects ボードは作らず、Issues のラベル（`story`、`sprint-1`〜`sprint-3`）で管理する（2026-10-30 オーナー決定）

## Phase 3：初期設計（どう作るか）

- **やること**：言語・ライブラリ・データの取り出し方などを ADR で決める。全体構成図を 1 枚描く（解析 → 推定 → master.db への書き込み → CLI / MCP）
- **成果物**：`docs/adr/NNNN-タイトル.md`、`docs/architecture.md`
- **決めるのは後から変えにくいことだけ**
  - Phase 3 で決める：言語、データの取り出し方、モジュール間でやりとりするデータの形（例：曲 → 推定キューのリスト）
  - スプリントで決める：クラス構成、推定ルールの中身、CLI のオプション
- 推定部分を差し替え可能にしておく。ルールベースを ML に置き換えても、評価スクリプトと DB への書き込みはそのまま使える

## MVP

MVP は「機能を最小にした製品」ではなく、**仮説を確かめるための最小の道具**として扱う。

| 意味 | 内容 | フェーズ |
|---|---|---|
| 範囲の設計 | どの機能を入れて何を確かめるか | Phase 1 で決め、Phase 2 で受け入れ基準まで落とす |
| 技術の設計 | 構成、データの流れ、モジュール分割 | Phase 3 で大枠、細部は Sprint 0〜3 の中で |

仮説の例（Phase 0 で確定させる）：

> 曲の構造の区切りと小節グリッドからルールでキューを打てば、手動で打つ時間を半分にできる

範囲のたたき台（Phase 1 で確定させる）：

- **入れる**：XML の読み込み、Rekordbox のグリッドの利用、ルールベースの推定、master.db への書き込み（[ADR 0001](adr/0001-write-cues-to-master-db.md)）、CLI、評価スクリプト
- **入れない**：ML モデル、MCP、GUI、自前の拍検出

## Phase 4：スプリント

個人開発向けに軽くしたスクラムで進める。

| イベント | やり方 |
|---|---|
| スプリント | 1 週間。ゴールは 1 つに絞る（例：F1 を測れるようにする） |
| 計画 | バックログから今週やるものを選び、Issue に `sprint-N` のラベルを付ける |
| 実装 | 小さなブランチと PR に分けて進める。Claude Code にレビューさせる |
| レビュー | 評価スクリプトの数値を見る。加えて、実際にキューを打った曲でミックスしてみる |
| 振り返り | KPT で 5 分。`docs/retro/` に 1 ファイル追加 |

スプリント計画のたたき台：

- **Sprint 0**：リポジトリ整備（README、`.gitignore`、ADR 置き場）、Python 環境、XML の取り込み
- **Sprint 1**：手動キューの統計と評価スクリプト
- **Sprint 2**：ルールベースのベースライン → 最初の F1 を出す
- **Sprint 3**：master.db にキューを書いて Rekordbox に反映 → 実際の DJ で使う（MVP 完成）
- **Sprint 4 以降**：ML モデル、MCP 化、精度改善。数値と使った感想を見て優先度を決める

## Phase 5：公開・まとめ

- README（目的、使い方、再現手順）
- 評価結果の推移
- ADR の一覧
- 全体の振り返り
