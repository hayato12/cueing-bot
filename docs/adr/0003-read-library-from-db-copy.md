# ADR 0003：ライブラリの情報は master.db のコピーと解析ファイルから読む

- 状態：**承認**（2026-10-30、オーナー）
- 関係する記録：[ADR 0001](0001-write-cues-to-master-db.md)、[ADR 0002](0002-python-and-tooling.md)、[スパイク 2](../spikes/02-phrase-analysis.md)、[スパイク 4](../spikes/04-db-write.md)、[requirements.md](../requirements.md)（S1・S2・決定 11）

## 背景

アプリが Rekordbox から読む情報と、その読み方を決める。CLAUDE.md の未決定事項「教師データの取り出し方」にあたる。最初の案は「XML エクスポート（公式の機能で読み取りだけ）」だったが、その後に次のことが分かった・決まった。

- 反映は master.db に直接書くことにした（ADR 0001）。pyrekordbox はどのみち使う
- フレーズ解析は XML に入っておらず、解析ファイル（`ANLZ0000.EXT` の `PSSI`）にしかない。曲と解析ファイルを確実に対応付けるには、master.db の `AnalysisDataPath` が要る（スパイク 2）
- master.db の**コピー**を pyrekordbox で開けば、暗号の鍵は自動で見つかり、手動キューのある 1,545 曲すべてで解析ファイルと対応付いた（スパイク 2 の追記）

## 選択肢

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A. XML エクスポート ＋ 解析ファイル | ユーザーが毎回 XML を書き出し、それを読む。フレーズ解析は解析ファイルをファイル名で対応付けて読む | 公式の機能。DB の形が変わっても XML は変わりにくい | **実行のたびに手で書き出す**（S2 の「1 曲ずつ操作したくない」に反する）。解析ファイルの対応付けがファイル名頼みで、取りこぼしがある（1,527／1,545 曲）。曲名入りの XML がたまる |
| **B. master.db のコピー ＋ 解析ファイル（推奨）** | 実行のたびに master.db（と `-wal`・`-shm`）を作業用のフォルダにコピーし、**コピーだけを**開いて読む。グリッドとフレーズは解析ファイルから読む | 手作業がない。全曲で解析ファイルと対応付く。書き込み（ADR 0001）と同じ道具で、曲の ID もそのまま使える。Rekordbox の起動中でも読める | 非公式の形を読むので、Rekordbox の更新で読めなくなるおそれがある（書き込みと同じリスク）。実行のたびにコピーの時間がかかる（大きさに比例し、Sprint 0 で測る） |
| C. 本物の master.db を読み取り専用で開く | コピーせずに開く | コピーの手間がない | Rekordbox の起動中に開くと、SQLite の仕組み上、読み取りでも `-wal`・`-shm` に触れることがある。ライブラリを壊さない（N1）ことを考えると、わざわざ取る理由がない |

## 推奨：B

- 推定・評価で読むときは、毎回 master.db のコピーを取り、コピーだけを開く。本物の master.db を開くのは、書くとき（ADR 0001）だけにする
- コピーは個人データなので、リポジトリの外（例：`~/llm/cueing-bot/data/`）に置く。保存する場所と、古いコピーを消すかは Sprint 0 で決める
- グリッドは解析ファイルの `PQTZ` を使う。XML の `TEMPO` と同じものかは Sprint 0 で数曲を比べて確かめる
- XML は使わない。評価データ b（オーナーが確認した 30 曲）は、XML ではなくアプリが書き出す CSV などで持つ（形は Sprint 1 で決める）

### 書くときに読み直すこと

推定はコピーで行うので、推定から書き込みまでの間に、ユーザーが Rekordbox でキューを打つことがある。そこで**書く直前に本物の master.db で、その曲の今のキューを読み直し**、手動キューが 1 つでもあれば書かずに飛ばす（決定 11）。**グリッドは master.db ではなく解析ファイルにあるので、解析ファイルの `PQTZ` も読み直す。** 推定のときのグリッドと違えば（推定のあとでグリッドが直されていれば）、その曲は書かずに「要確認」にする。ms への変換には読み直したグリッドを使う（[architecture.md](../architecture.md) 3 章）。

### コピーが壊れていないかを確かめる

Rekordbox の起動中にコピーを取ると、`master.db` と `-wal` をコピーする間に Rekordbox が書き込み、組み合わせの合わないコピーになることがある。本物は壊れないが、キューの一部が欠けたコピーを正解として読むおそれがある。そこで、コピーのあとに `PRAGMA integrity_check` をかけ、コピーの前後で 3 つのファイルの更新日時が変わっていないかも見る。どちらかが外れたら、コピーし直す。

## 決定

**B. master.db のコピー ＋ 解析ファイルから読む。** XML エクスポートは使わない。

- 推定・評価では、毎回 master.db（と `-wal`・`-shm`）のコピーを取り、コピーだけを開く。本物の master.db を開くのは書くときだけ
- グリッドは `PQTZ`、フレーズは `PSSI` を解析ファイルから読む
- 書く直前に本物の master.db でその曲のキューを読み直し、手動キューがあれば飛ばす。グリッドが変わっていれば書かずに「要確認」にする

## 結果

- CLAUDE.md の未決定事項「教師データの取り出し方」を決定済みに移した。技術メモの XML の項目は、「使わない」と分かるように直した
- Rekordbox の更新で DB の形が変わると、読むところも書くところも影響を受ける。ADR 0001 と同じく、Rekordbox のバージョンを確かめ、確かめたバージョンと違えば警告する
- pyrekordbox が読めない解析ファイル（スパイク 2 で 11 曲）は、推定せずに「失敗」の一覧に出す（N9）

## 追記（2026-10-31、Sprint 0 の実装）

- コピーするのは `master.db`・`-wal`・`masterPlaylists6.xml` で、**`-shm` は写さない。** `-shm` は SQLite が開くときに `-wal` から作り直すもので、Rekordbox が読むだけでも更新される。コピーの前後比べに入れると、Rekordbox の起動中はいつまでもコピーが取れなくなる
- コピーの確かめは `PRAGMA integrity_check` ではなく `quick_check` にした。組み合わせの合わないコピーは見つけられ、全ページの照合を省けるぶん速い
- コピーの置き場は data フォルダの `tmp/`。読み終わったら消す
- 2026-10-31 にオーナーの Mac で確かめた：master.db 36MB・`-wal` 4MB のコピーと確かめが 0.2 秒（Rekordbox の起動中、1 回目で取得）。9 曲のプレイリストを失敗なく読めた
- `PQTZ` と XML の `TEMPO` を 3,063 曲で比べ、87% が 1 ms 以内、99.8% が 20 ms 以内で一致した。小さなずれは XML の BPM が小数 2 桁に丸められているためとみられる。グリッドは `PQTZ` を使ってよい
