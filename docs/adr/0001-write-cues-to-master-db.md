# ADR 0001：キューは Rekordbox の master.db に直接書いて反映する

- 状態：**承認**（2026-10-30、オーナー）。USB への書き出しと XDJ-RR での呼び出しは、後日オーナーが確かめる（下の「まだ確かめていないこと」）
- 関係する記録：[スパイク 3](../spikes/03-xml-import.md)、[スパイク 4](../spikes/04-db-write.md)

## 背景

アプリが推定したキューを Rekordbox に入れる方法を決める必要があった（[requirements.md](../requirements.md) の 4）。
最初は「出力は XML、DB には書かない」と決めていた（CLAUDE.md の作業の約束）。公式の機能だけを使い、ライブラリを壊すおそれがないためである。

ところがスパイク 3 で、Rekordbox 7.2.18 の XML 取り込みには次の制限があると分かった。

- **メモリーキューは 1 曲に 1 つしか入らない。** MVP では 1 曲にメモリーキューを 2 つ打つ（A メロの頭と、その 2L 小節前）ので、足りない
- 取り込むと、曲のキューは XML の内容に丸ごと置き換わる。取り込みの確認のダイアログで「はい」を選べば TrackID・プレイリスト・レーティング・myTag は残るが、ダイアログが出ずに曲が新しく足され、プレイリストから外れたこともあった（スパイク 3 の 1 回目。原因は不明）

## 選択肢

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A. XML の取り込み | XML を出力し、ユーザーが「rekordbox xml」から取り込む | 公式の機能。DB の形を知らなくてよい | メモリーキューが 1 つしか入らない。ダイアログの答え方などによっては TrackID が変わり、プレイリストから外れる。取り込みの手作業がいる |
| B. master.db に直接書く | pyrekordbox で `djmdCue`・`contentCue`・`djmdContent` を書く | メモリーキューを何個でも書ける。プレイリストや曲の情報に触れない。取り込みの手作業がいらない | 非公式。書き方を誤るとライブラリを壊すおそれがある。Rekordbox の更新で DB の形が変わるおそれがある。Rekordbox を閉じてから書く必要がある |
| C. XML ＋ 手で打つ | XML で 1 つ入れ、残りはユーザーが画面で打つ | 公式の機能だけ | 手間を 1/3 以下にする目標（concept.md）から遠い |

## 決定

**B. master.db に直接書く。**

スパイク 4 で、テスト用の曲（デモ曲のコピー）に書いて確かめた（2026-10-30）。

- MP3（CBR、2 曲）と M4A（1 曲）に、メモリーキューを 3 つずつ書けた
- Rekordbox の画面に 3 つとも出て、それぞれから再生すると狙った小節の頭から鳴った
- ほかの曲のキューは変わらなかった。ライブラリ全体で、`djmdCue` と `contentCue` の食い違いは 0 のまま

## 書くときの決めごと

スパイク 4 の [spike4_write_cues.py](../../scripts/spikes/spike4_write_cues.py) の書き方をもとにする。

1. **Rekordbox を終了してから書く。** 起動中なら書かずに止める（pyrekordbox の `commit()` も止まる）。**常駐の rekordboxAgent も止まっていること、master.db を開いているプロセスがないことも確かめる**（本体を終了しても rekordboxAgent が DB を開いていることがあった。スパイク 4）
2. **書く前に必ずバックアップを取る。** `master.db`・`master.db-wal`・`master.db-shm` と `masterPlaylists6.xml` を日時付きのフォルダにコピーする（`masterPlaylists6.xml` は Rekordbox の終了時に更新される。スパイク 4）。取った直後にコピーを開き、`PRAGMA integrity_check` が通ること、`djmdCue` の行数と `contentCue` の要素数が全曲で一致することを確かめる。確かめられなければ書かない
   - **戻すとき**は、Rekordbox と rekordboxAgent を終了してから、(1) 今のファイルを別のフォルダに退避する、(2) 今の `master.db-wal`・`master.db-shm` を消す、(3) バックアップにあるファイルだけを元の場所に置く。今の `-wal` を残したまま古い本体を戻すと、SQLite が古い本体に新しい WAL を当てて DB を壊すことがある
   - 戻す手順も、テスト用の曲で一度試しておく（requirements.md の D7）
3. **Rekordbox 自身と同じ形で書く。**
   - `djmdCue`：画面で打ったキューと同じ形（`Color` -1、任意の列は NULL、`InFrame` = floor(InMsec × 150 / 1000)、MPEG の列は 0、`OutMsec` -1）
   - `contentCue`：その曲の全キューの JSON を書き直し、`djmdCue` とそろえる
   - ホットキューは `Kind` でパッドを表す（A〜C が 1〜3、D〜H が 5〜9、4 は使わない）。色の列は空でよい（Rekordbox の既定の色になる）
   - `djmdContent.CueUpdated` を増やし、USN を `contentCue` → 曲の行の順に 1 ずつ進める
4. **書くのはアプリが対象にした曲のキューだけ。** プレイリスト・曲の情報・ほかの曲には触れない
5. **書く内容を先に見せる。** 既定は表示だけにし、ユーザーが確かめてから書く

## 結果

- CLAUDE.md の「出力は XML、DB には書き込まない」を、「DB に書くときは上の決めごとを守る」に改める
- XML はキューの反映には使わない。教師データの読み込みにも使わない（[ADR 0003](0003-read-library-from-db-copy.md)）
- Rekordbox の更新で DB の形が変わると、書けなくなったり壊したりするおそれがある。書く前に Rekordbox のバージョンを確かめ、確かめたバージョン（7.2.18）と違えば警告する
- 書き込みは pyrekordbox に頼る。スパイク 4 は 0.4.4 で確かめた。アプリでは 0.5.0（Python 3.11 以上が必要）に上げ、Sprint 3 でテスト用の曲を使って確かめ直す（[ADR 0002](0002-python-and-tooling.md)）

## まだ確かめていないこと

| 項目 | 内容 | 予定 |
|---|---|---|
| USB への書き出しと XDJ-RR | DB に書いたキューが USB の解析ファイルに入り、XDJ-RR で呼び出せるか。XDJ-RR の世代は旧い形式（`PCOB`）を読むので、Rekordbox が両方を作り直すか | オーナーが後日確かめる。**ここで問題が出たら、この ADR を見直す** |
| VBR の MP3 | Rekordbox が MPEG のフレーム位置を必要とするか（pyrekordbox の作者が懸念している点） | ライブラリの MP3 は 412 曲。実装の前に 1 曲で確かめる |
| WAV・FileType 25/26 などほかの形式 | M4A・MP3 と同じく `InMsec` だけで位置が決まるか | 必要になったら確かめる |
| XML エクスポート | DB に書いたキューが XML のエクスポートに入るか | 確かめるなら手間は小さい |
| クラウドライブラリ同期 | オンにしている場合、直接の書き込みがどう扱われるか | オーナーは使っていない（2026-10-30 確認）。使う人向けに公開するなら確かめる |
